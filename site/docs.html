Hydra Terminal

Hydra Terminal watches what specific crypto wallets actually do on-chain — not what people say, not sentiment, not price alone — and turns that into a live LONG / SHORT trading signal and a BULL / BEAR market-regime read for ETH. This page explains the idea, the mechanism, and the codebase, for anyone joining the project without a crypto background.

Ethereum mainnet — live Hyperliquid ETH-PERP — live, blended into signal Base L2 — live, blended into spot (B1–B3)

Overview

At the highest level, Hydra runs an hourly pipeline that: pulls raw trade data from three independent sources, scores every wallet it has seen as a historically GOOD or BAD trader, aggregates what those two groups are doing right now, and turns that into two separate outputs — a short-term trading signal and a longer-term market regime — which are published to a static dashboard.

Nothing here predicts price from price. The entire bet the project is making is that a cohort of wallets with a strong historical track record behaves as a leading indicator: when they start buying before everyone else, the aggregate signal should tend to lead the market rather than follow it. Whether that bet actually holds is an open, ongoing empirical question — not an assumption baked into the code.

Where this comes from

Hydra Terminal is a from-scratch reconstruction of the mechanism behind hydra.trading, a site that published a live ETH signal derived from classifying DEX wallets into good/bad cohorts. The original project's source and infrastructure were lost, so this codebase re-derives the approach from first principles — reading the same on-chain events, applying the same kind of classification and scoring logic, and rebuilding the pipeline as open, auditable, public code rather than a black box.

The project has since grown beyond the original single-pool design: it now blends in two further, independent data sources — perpetual futures on Hyperliquid, and spot swaps on Base (an Ethereum Layer 2) — specifically to grow the pool of wallets being tracked and to see whether the signal holds up across venues. Base was added after noticing that Uniswap mainnet was tracking far fewer wallets than Hyperliquid; see Data source: Base L2 below for why, and what changed.

Both Hyperliquid and Base follow the same four-phase rollout pattern, so you'll see it referenced throughout this codebase and its history:

Phase 0 — Collect

Pull raw trades into an isolated buffer. No effect on the live signal yet.

Phase 1 — Classify

Score wallets from that source as GOOD / BAD, same method as mainnet.

Phase 2 — Blend

Merge that source's composite score into the signal the dashboard shows.

Phase 3 — Surface

Give the new source its own visible breakdown on the frontend — a dedicated card (Hyperliquid) or its own row within an existing one (Base's Wallets-card row, its own line in the Spot tile's tooltip).

Why phase it like this

Every new data source is wired in fully isolated at first — its own state file, its own error handling, its own code path — specifically so that a problem with a brand-new, unproven source (a bad RPC endpoint, a rate limit, a parsing bug) can never take down the mainnet pipeline that's already working. Only once a source is collecting cleanly does it get promoted to actually influencing what a viewer sees.

Core concepts: wallets & addresses

On Ethereum (and Base, which is built to be compatible with it), an account is identified by an address — a 42-character hex string like 0x4200...0006. There's no name, email, or KYC attached to it at the protocol level; anyone can generate one for free. A single person can control any number of addresses.

Every transaction sent from an address is public, permanent, and free for anyone to read — that's the entire premise the project rests on. Hydra doesn't need permission or an API key from any exchange to see what a wallet is doing; it reads the same public ledger everyone else can read, just at scale and automatically.

Hydra never tries to attach a real-world identity to an address. It only cares about one thing per wallet: given its trading history, was this address historically a good or a bad trader?

Core concepts: DEX pools & swaps

A DEX (decentralized exchange) like Uniswap doesn't match buyers with sellers order-book style. Instead, it uses a liquidity pool: a smart contract holding a reserve of two tokens (here, WETH — wrapped ETH — and USDC, a US-dollar stablecoin). Anyone can deposit both tokens into the pool to earn trading fees; anyone can trade against that reserve at any time.

A swap is a trade against that reserve: send USDC in, receive WETH out (a buy of ETH), or the reverse (a sell). Every swap emits a public Swap event on-chain, containing the pool, the amounts of each token, and the address that triggered it. That event is the single raw ingredient the mainnet and Base data collectors read — nothing more exotic than "who swapped how much, which direction, when."

Hydra originally tracked a single Uniswap V3 USDC/WETH 0.05% fee pool — one of the deepest, most actively traded ETH/USD venues on Ethereum, chosen and verified directly against the on-chain contract rather than assumed from a third-party list. It now reads from nine pools on Ethereum mainnet: six on Uniswap V3 (three USDC/WETH fee tiers, three WETH/USDT fee tiers — the third tier on each pair, 0.01%, added 2026-09-18 after they turned out to be the two highest-volume mainnet pools not yet tracked) and, as of 2026-09-17, three on PancakeSwap V3 — an architecturally identical fork of Uniswap V3 (same Swap event, same on-chain mechanics), added to widen the pool of tracked wallets without touching the decoding pipeline at all.

Core concepts: perpetuals

A perpetual future ("perp") is a derivative contract that tracks an asset's price without ever settling or expiring — traders open long or short positions with leverage, and a funding-rate mechanism keeps the contract's price tethered to the real spot price. Unlike a DEX swap, a perp trade doesn't require actually owning the underlying asset.

Hyperliquid is a decentralized perpetuals exchange, and one of the largest venues for on-chain perp trading. Hydra tracks its ETH-PERP market specifically — a completely different population of traders than the spot Uniswap pool, since perp traders and spot traders are often different people with different behavior. That's the whole reason it was added: to grow and diversify the wallet base beyond a single pool on a single chain.

Technically, Hyperliquid doesn't offer a REST endpoint for "everything that traded in the last hour" the way a block-based chain does — discovering new wallets requires a persistent WebSocket subscription to its public trade firehose, which is why the Hyperliquid side of the pipeline runs as a long-lived listener rather than the hourly "wake up, ask, go back to sleep" pattern used for mainnet and Base.

Core concepts: what is a Layer 2

Ethereum's own capacity is limited, which makes transactions there relatively slow and expensive. A Layer 2 (L2) is a separate blockchain that processes transactions independently but periodically settles back to Ethereum for security — cheaper and faster, while still inheriting Ethereum's guarantees.

Base is an L2 built by Coinbase. It has its own block numbers, its own block time (~2 seconds, versus Ethereum's ~12), and its own instance of the same Uniswap V3 contracts — including a WETH/USDC 0.05% pool, verified on-chain the same way as the mainnet one. Because it's a separate chain, its block numbers aren't comparable to Ethereum's at all, which is why Base is tracked as a fully independent data stream with its own cursor and buffer rather than mixed into the mainnet one.

Classifying wallets: GOOD / BAD

Every wallet Hydra has seen trade gets a rolling profit-and-loss (P&L) calculated with an average-cost method (covering both long and short exposure), plus a win rate across its trades. Wallets are then ranked against each other by that historical performance and split into three cohorts:

  • GOOD — roughly the top ~15% by historical performance.
  • BAD — roughly the bottom ~15%.
  • NEUTRAL — everyone in between; not used in scoring.

This classification is recalculated periodically as new data comes in (roughly every 250 blocks on mainnet, on the order of an hour), and — critically — a wallet is only ever classified using information available up to that point in time. Its future trades are never used to judge its past behavior. This "no look-ahead" rule is enforced deliberately, because without it a backtest of this whole approach would be meaningless — it would just be fitting to the answer.

Why this matters for the science, not just the code

The entire hypothesis under test is "does the aggregate behavior of historically-good wallets predict future price action." That's only a real test if the classification at time T could not have known what happens after T. Every classification pass in this codebase respects that boundary.

A wallet also needs a minimum number of qualifying trades (see the dust filter) within the reputation window before it's classified at all — too little history and it's simply left out, not forced into a cohort. That minimum is 3 trades for both DEX sources (Uniswap mainnet and Base — lowered from 5 on 2026-09-17, once a check against the live 7-day trade buffers showed it excluding a large share of otherwise real, above-dust wallets: 86% more mainnet wallets and 41% more Base wallets become eligible at 3 than at 5) and stays at 5 for Hyperliquid — the two sources use separate config classes (ScoringConfig/HyperliquidScoringConfig) specifically so a threshold like this can differ without touching the other, reflecting that on-chain trading (gas cost per trade) and perp trading (cheap, frequent) build up a track record at very different rates.

Composite score

For each scoring window, Hydra measures net buy/sell pressure separately for the GOOD cohort and the BAD cohort — essentially, "of all trading volume from good wallets this window, what fraction was buying versus selling," and the same for bad wallets. Those two pressures are smoothed with a short and a long exponential moving average (EMA) each, giving four tracked indicators per window, and combined into a single composite score: positive when good wallets are net buying (and/or bad wallets are net selling), negative in the opposite case.

Three independent sources feed the pipeline — Uniswap on mainnet, Uniswap on Base, and the ETH-PERP market on Hyperliquid — organized into two decision pools: SPOT (Uniswap mainnet + Base, pooled together) and PERP (Hyperliquid, with room to add another perpetuals venue later). The two pools are combined in a single blend stage: 

composite_spot_combined = spot_pool(uniswap_counts + base_counts)
composite_final         = blend(composite_spot_combined, composite_perp, weight=0.5)

Uniswap and Base used to be combined the same way as SPOT/PERP above — a fixed 50/50 blend of two independently-smoothed composite scores. That changed on 2026-09-11: a fixed weight gave Base exactly half the influence over the spot value regardless of how many wallets actually traded on Base that hour, even when Base's classified sample for the window was a handful of wallets against Uniswap's several dozen. Instead, Uniswap's and Base's raw per-window counts (how many GOOD/BAD wallets bought vs. sold) are now summed into one shared pool before computing a single ratio and a single EMA — so each source's influence is proportional to how much it actually traded that window, not a fixed constant. When Base has no classified activity in a window (immature or unconfigured), it contributes zero to the pool and the result reduces to Uniswap alone — the same graceful-degradation guarantee as before, just implemented as "contributes nothing" rather than "gets excluded from a blend."

As of 2026-09-11's "volume weighting" phase, the shared SPOT pool runs a second, parallel track alongside the wallet-count one above: each wallet's net position for the window is additionally weighted by sqrt(min(notional_usd, cap)) instead of counting as a flat "1" regardless of trade size. The square root dampens the effect of outsized trades — a $1M trade counts noticeably more than a $1K one, but only about 32×, not 1,000× — and the fixed dollar cap (ScoringConfig.volume_weight_cap_notional_usd, $50,000 by default, applied before the square root) puts a hard ceiling on any single trade's weight. A cap based on a percentile of each window's own volume was considered and rejected: with the small per-window sample sizes this project currently sees (often just a handful of classified wallets), a percentile computed from the window itself would be statistically meaningless — with three trades in a window, the "95th percentile" is just the largest of the three, no real ceiling at all. A fixed dollar figure, tunable later like every other threshold in this project, is more robust to that.

This volume-weighted track keeps its own EMA, entirely separate from the wallet-count track, and the two are blended 50/50 (ScoringConfig.volume_weight_blend) into the final composite_spot_combined. That blend is a deliberate third layer of protection against a single large wallet ("whale") dominating the result: even if the volume-weighted track were fully skewed by one outsized trade, it can only move half of the final value — the other half always comes from the wallet-count track, which is immune to trade size by design (one wallet, one vote). When a caller doesn't supply any volume data at all (for example, code written before this phase), the pool falls back to the wallet-count track alone, unchanged — the same graceful-degradation pattern used throughout this pipeline.

The SPOT ↔ PERP stage above still uses the older graceful-fallback blend function: whenever Hyperliquid doesn't yet have enough classified wallets to be considered statistically mature (see Data source: Hyperliquid), that blend collapses to just composite_spot_combined, unchanged. composite_spot itself stays mainnet-only throughout, purely as a diagnostic baseline — composite_spot_combined is the pooled SPOT value that actually carries Base's contribution forward into the final blend. composite_base (Base's own, independently-smoothed score) is likewise kept only as a diagnostic field — it no longer feeds the decision directly. (Until 2026-09-13, composite_spot was also what the "sam spot" divergence note on the dashboard compared against — see the addendum below for why that changed.)

A small addendum, 2026-09-12: after shipping the volume-weighting phase above, the project owner asked whether the split between the wallet-count track and the volume-weighted track would ever be visible anywhere in the UI — it wasn't, on purpose, since both tracks lived only inside SpotPoolEngine and were never exposed past the single blended value. Two new diagnostic-only instance attributes, last_composite_counts and last_composite_weighted, now record each track's own composite as a side effect of every update() call — a snapshot for the calling run to read immediately afterward, not resumable state: they deliberately live outside export_state(), since resuming the EMAs across runs never needed them, only this run's own diagnostic read does. run_incremental.py copies them onto the candle as spotPoolCompositeCounts and spotPoolCompositeWeighted, following the same null-means-"not supported yet" convention as every other optional candle field in this project — a candle produced before this phase, or by any run that never activated the volume-weighted track, carries null for both, and the dashboard treats that as "hide this," not "zero." Only these two composites are exposed, deliberately not the underlying pooled sqrt(min(notional_usd, cap)) weight sums themselves (pool_good_buy_weight and its siblings) — those are dampened, capped sums, not literal dollar amounts, and showing them next to a real-dollar candle price would misleadingly suggest otherwise. See Reading the terminal for where this surfaces on the page.

A third addendum, 2026-09-17 ("dzienny bilans GOOD/BAD" phase): the project owner asked for a daily buy/sell summary chart, with one hard condition stated up front — "to muszą być prawdziwe dane, nie zmyślaj" (this has to be real data, don't make it up). Two genuinely real sources exist for this: the per-window GOOD/BAD wallet counts (goodBuyers/goodSellers/ badBuyers/badSellers and their base*/ perp* counterparts) that every candle has always carried, and — new this phase — four raw dollar sums per WindowScore: good_buy_usd, good_sell_usd, bad_buy_usd, bad_sell_usd (mirrored on HyperliquidWindowScore, and inherited by Base for free since it reuses the same ScoringEngine class as mainnet). These reuse the exact same per-window wallet_notional[wallet] map already computed for the sqrt(min(notional_usd, cap)) weighting described above, but sum the literal notional — no square root, no cap — because the point here is an honest dollar figure for display, not a whale-dampened score for the signal. run_incremental.py copies them onto every candle as goodBuyUsd/goodSellUsd/ badBuyUsd/badSellUsd (mainnet), plus base*Usd/perp*Usd variants, all defaulting to 0.0 for backward compatibility with state files written before this phase. A genuine limitation follows directly from "don't make it up": these dollar sums can only start accumulating from the first pipeline run after this phase deploys — there is no way to reconstruct historical per-trade USD volume for blocks already processed (mainnet/Base trade buffers only ever stored block numbers, not per-trade timestamps, and resolving historical block→timestamp mappings would need live RPC access this project doesn't have standing infrastructure for outside the live collectors). So every candle from before deployment simply has no such field (or, after .get(key, 0.0) defaulting on the Base/Hyperliquid side, reads as exactly $0) — the dashboard shows that plainly rather than estimating a number. The wallet-count fields have no such gap: they've been written to candles_history.json (never pruned — see Per-run manifests for what is pruned) since long before this phase, so the daily chart's bar history reaches back as far as real data exists, even though its USD line only reaches back to deployment day. See Reading the terminal for how the card built from these fields reads and what it deliberately does not claim.

A second addendum, 2026-09-13: the hero's divergence banner ("Uwaga: sam spot ... wskazywałby ...") used to compare the final signal against signalSpotOnly — a naive, non-hysteresis signal computed from composite_spot, i.e. mainnet Uniswap alone. That predates both "integracja Base B1-B3" and "wspólna pula SPOT" — the project owner noticed, correctly, that the banner's own wording ("sam spot (Uniswap)... o finalnym sygnale zadecydował zblendowany wpływ Base i/lub Hyperliquid") no longer matched reality: Base has been part of the SPOT decision pool for weeks, so blaming it as a cause standing alongside "spot" was stale framing, not a fresh observation. The fix adds a new field, signalSpotCombinedOnly — the same naive decide_signal() check as signalSpotOnly, but run on composite_spot_combined (Uniswap+Base pooled) instead of mainnet alone, and against the same entry threshold the real SignalEngine uses (signal_engine.cfg.enter_threshold, 0.35) rather than the older, otherwise-unused ScoringConfig.signal_threshold (0.2) that signalSpotOnly still uses — an apples-to-apples "would spot alone cross the same bar" check. The banner now reads "sam spot (Uniswap+Base) wskazywałby ... — o finalnym sygnale zadecydował wpływ Hyperliquid i/lub historia potwierdzeń", dropping Base from the list of possible causes (it's baked into "spot" now) while keeping an "i/lub" hedge between Hyperliquid and confirmation history rather than committing to "Hyperliquid" outright. That hedge is deliberate, not leftover caution: this exact Base-B1-B3-era comment thread already found, via a Playwright scenario with a mature Base and a None (immature/unconfigured) perp, that a naive threshold comparison can name "Hyperliquid" as the cause even when composite_perp is None that candle — i.e. when Hyperliquid contributed literally nothing and the only real cause was SignalEngine's hysteresis/confirmation-period state carrying forward a prior decision. Verified with four Playwright scenarios: a normal divergence with Hyperliquid actually contributing, that exact compositePerp = None edge case (banner text stays true in both, precisely because of the hedge), no divergence (banner hidden), and a candle predating this phase entirely, i.e. missing the new field (banner hidden — the same graceful-degradation pattern as every other optional field here). signalSpotOnly itself is untouched and still exported on every candle (a public field of candles_history.json — removing it would be a breaking change for anyone scraping it), it's simply no longer what the banner compares against.

Candles & windows

Mainnet data is aggregated into fixed 250-block windows (roughly 50 minutes at Ethereum's ~12-second block time) — the same unit hydra.trading's original engine used, recognizable in this codebase as a "candle." A window only becomes a scored candle once enough blocks have passed beyond it to be confident it's complete; this is a deliberate, by-design lag, not a bug — it means the timestamp on the terminal's most recent candle will typically read 40–50 minutes behind the wall clock, even though the pipeline itself may have run only minutes ago. The separate "data last updated" indicator in the dashboard's topbar tracks the actual last successful pipeline run, distinct from the candle's own window-close time.

The signal: LONG / SHORT / HOLD

The blended composite score, once smoothed, is compared against a threshold to produce the headline signal shown in the terminal's hero: LONG, SHORT, or HOLD when neither side has enough conviction. The signal persists until the composite score moves decisively enough in the other direction — it isn't recomputed from scratch as a coin flip every window, which avoids flipping back and forth on small, noisy swings (the same hysteresis idea used for market regime, described next).

The dashboard also tracks every past signal period as a "streak" and reports its outcome — did the price move in the direction the signal implied by the time it ended — plus a running win rate across all closed streaks. That's the project's own scoreboard for whether the underlying hypothesis is actually working, kept visible rather than hidden.

Market regime: BULL / BEAR / NEUTRAL

The signal answers "what should I do right now" — it says nothing about the broader environment. A second, fully independent model answers a different question: "what kind of market are we in?" It's possible (and meaningful) for the regime to read BULL while the short-term signal is SHORT — a bullish backdrop with a short-term pullback — and the two are deliberately never conflated on the frontend.

Regime detection looks at the same GOOD/BAD cohort data but focuses on change over time rather than a single snapshot: is buy/sell pressure from good wallets improving or deteriorating across multiple horizons (1h out to 30d), is there a growing divergence between what good and bad wallets are doing, and how many individual good wallets have just flipped direction (e.g. closing a short streak and opening a buying one). Those signals feed two 0–100 scores, BULL_SCORE and BEAR_SCORE, which only produce a regime once they clear a threshold and hold for several consecutive windows — a persistence requirement that exists specifically to prevent a single noisy candle from flipping the whole regime read.

Two additional, rarer events are tracked on top of BULL/BEAR: CAPITULATION (bad wallets selling hard while good wallets are absorbing that supply — often a precursor to a bull transition, not the transition itself) and DISTRIBUTION (the mirror case — good wallets quietly selling into bad wallets buying, often ahead of a bear transition). Both are shown in a dedicated regime event log on the dashboard.

Data source: Ethereum mainnet

The original and still primary source: Swap events from nine pools on Ethereum mainnet, read via JSON-RPC (eth_getLogs plus transaction lookups to resolve the real sender). Six are Uniswap V3 (USDC/WETH at 0.01%, 0.05% and 0.3%, WETH/USDT at 0.01%, 0.05% and 0.3% — the 0.01% tier on each pair added 2026-09-18, after a volume review found they were the two largest mainnet pools not yet tracked, ≈$51M and ≈$20.5M/24h respectively at the time); three, added 2026-09-17, are PancakeSwap V3 (USDC/WETH 0.01%, WETH/USDT 0.01% and 0.05%) — PancakeSwap V3 is a verbatim fork of Uniswap V3's contracts, so the same event signature, decoder, and batching logic cover both without any code branching per DEX. All addresses are batched into a single eth_getLogs filter, so adding pools costs nothing extra in RPC calls, only in response size. Because the RPC provider used (Alchemy, free tier) hard-limits eth_getLogs to a 10-block range per call, the collector issues many small ranges as a single batched JSON-RPC request rather than hundreds of individual round trips, with automatic retry on any call that fails or gets rate-limited.

Data source: Hyperliquid (ETH-PERP)

A persistent WebSocket listener subscribes to Hyperliquid's public trades channel for the ETH market, which streams every trade with both counterparties' addresses. Collected trades are buffered (currently a 30-day retention window — raised from 7 days as of the "Long term (30d)" phase, see below, so the same buffer can feed both the original 7-day classification and the new, longer one) and periodically classified with the same wallet-scoring method as mainnet, entirely independently — Hyperliquid has its own state files, its own classification pass, and its own composite score, which is only combined with the mainnet one at the very last step described above.

Because the buffer can grow larger than GitHub's 100MB-per-file push limit, it is deliberately kept out of git history entirely and stored instead in GitHub Actions' own cache between runs.

Data source: Base L2 Phase B1–B3

Base's Swap events from its own WETH/USDC 0.05% Uniswap V3 pool are collected the same way as mainnet (batched eth_getLogs), but into a completely separate buffer and block cursor — Base's block numbers have nothing to do with Ethereum's, and its ~2-second block time means covering the same wall-clock window costs roughly 6x as many RPC calls as mainnet does.

As of the "Base B1–B3" phase (2026-09-11), collected Base trades are also classified and blended in — Base is no longer collection-only. It reuses mainnet's own generic ScoringEngine/ScoringConfig directly (a second, independent instance with its own state), rather than a whole new engine class the way Hyperliquid needed — Base's collected trade shape already matches the generic Trade dataclass exactly, so no adapter layer was necessary:

ParameterValueWhy
BASE_WINDOW_BLOCKS1,8003600s / ~2s per block ≈ same ~1h candle cadence as mainnet's 250-block window (250 × ~14.4s)
BASE_CLASSIFICATION_LOOKBACK_BLOCKS302,4001,800 × 24 × 7 — same ~7-day reputation window used elsewhere, on Base's own block grid
BASE_MIN_CLASSIFIED_WALLETS_FOR_MATURITY20Maturity gate before Base's per-window counts are allowed into the shared SPOT pool — identical default to Hyperliquid's own threshold

As of the "Long term (30d)" phase (see below), Base's trade buffer retention was also raised (310,000 → 1,330,000 blocks, ~30 days + margin) so it can feed a second, longer-lookback classification pass alongside this one, without any additional RPC calls.

BASE_SPOT_WEIGHT (a fixed 50/50 blend weight) existed here until 2026-09-11's "shared SPOT pool" change — see Composite score for why it was removed and what replaced it. Below the maturity threshold, Base's window counts (good/bad buyers-sellers) are treated as zero when building the shared pool, and the pooled value degrades to mainnet alone — exactly the same graceful fallback Hyperliquid uses for composite_perp. Wallets are tracked, classified, and shown on the Wallets card the whole time regardless of maturity — the gate only controls whether Base's counts are allowed to move the pooled SPOT value, not whether Base activity is visible at all.

Because Base's engine reuses the exact same ScoringConfig class as mainnet (see above), it also computes its own sqrt(min(notional_usd, cap))-weighted per-window sums with the same default $50,000 cap — see Composite score for the "volume weighting" phase — and those weighted sums are pooled into the shared SPOT value the same way its raw buyer/seller counts are, subject to the same maturity gate above.

A deliberate one-run lag

Base's RPC-fetching step has to stay at the very end of main() (see the incident below), which means Base's newly-computed composite_base can't be blended into the same run's own candles — by the time Base finishes scoring, the site has already been generated. Instead, each run reads whatever composite_base the previous run computed and persisted, and blends that into its own new candles. In practice: Base's contribution to the signal is always approximately one hourly cycle stale relative to Base's own newest data — never zero, but bounded and predictable, and preferred over risking the RPC reordering that caused the incident below.

A real incident worth knowing about

On Base's very first live run, its own RPC burst was large enough to exhaust the shared Alchemy account's throughput budget so badly that it broke the mainnet pipeline's own critical call, aborting the entire run with zero data saved — even for the parts that had nothing to do with Base. The fix was architectural: the Base collection (and, since B1–B3, scoring) step was moved to run strictly after the mainnet+Hyperliquid path has already finished and saved its results, so a Base-side problem can now only ever affect Base's own data, never anything that already succeeded. See Reliability lessons below — it's a pattern worth understanding before touching this part of the code.

Long term (30d) classification track Phase 1 + 2 shipped

Every wallet-classification pass described above (mainnet, Base, Hyperliquid) uses a reputation window — how much of a wallet's own trading history is used to judge it GOOD or BAD (see Classifying wallets). That window has been 7 days everywhere since the "reputation window 7 days" phase (2026-09-01). As of 2026-09-14, a second, fully parallel copy of the entire classification and scoring pipeline now also runs alongside the original on every hourly run — identical in every way except that it classifies wallets using a 30-day window instead of 7.

This is not a new data source and not a replacement for the existing 7-day track — both run side by side, permanently, on exactly the same already-collected trades. It costs zero additional RPC/Alchemy calls: the only real cost is retaining more of the raw trade history that was already being fetched (see the widened buffer-retention defaults for Hyperliquid and Base above), and somewhat more state on disk. A few pieces of state that don't actually depend on the length of the reputation window — the set of every wallet ever seen, and each wallet's buy/sell streak used for Wallet Flip detection — are shared between the two tracks rather than duplicated, since they'd be identical either way.

Every value the 30-day track produces is written to data/candles_history.json alongside the existing 7-day fields, under the same name with an Lt suffix (for "long term") — e.g. signalLt, compositeLt, regimeLt, bullScoreLt. The name deliberately avoids "30d", which already means something else entirely in this codebase (a momentum look-back horizon — see Composite score and Market regime) — reusing it here for a completely different kind of "30 days" would have been confusing in the code, even though both are shown to a person as "30 days."

The dashboard exposes this as a "Long term" tab next to "Main", above the hero section. Clicking it doesn't load a second copy of the page — the exact same hero, composite meters, Wallets card, market-mood card, price/signal chart and signal-history table simply re-render themselves against the 30-day track's data instead of the 7-day track's (a small client-side trackView() function remaps each Lt-suffixed field back onto its plain name before handing the candle to the same rendering code — a mirror image of the _synthetic_lt_view() technique live/run_incremental.py uses server-side to feed the 30-day candles through the same regime/momentum code as the 7-day ones). One field, pool (the Wallets tooltip's "Uniswap scoring pool" count), has no poolLt counterpart in the data at all — unlike the genuinely track-independent fields below, it depends on which reputation window classified the wallets, so it's derived on the fly in the browser as goodBuyersLt + goodSellersLt instead.

A track that starts empty

The 30-day track only started accumulating history from the moment Phase 1 shipped, so existing candles from before that point simply don't carry any Lt-suffixed fields at all (not null — absent). The "Long term" tab treats "this candle has a signalLt field" as the test for "belongs to this track's history," so right after launch it can legitimately show an empty chart, dashes in the Wallets card, and a "zbieramy historię tego toru" (gathering history) note in place of the hero pill and mood card — that's the track correctly reporting it has nothing yet, not a bug. It fills in candle by candle as the hourly pipeline runs, and will only reflect a genuinely deep 30 days once it's been running for about that long (exactly how the original 7-day track behaved when it first shipped).

Automation & state

The whole pipeline runs unattended via GitHub Actions, on an hourly schedule for the mainnet/Hyperliquid-blend/Base run (update.yml), plus a continuously-running listener workflow for Hyperliquid's WebSocket feed (hyperliquid-update.yml). Each run is incremental: it picks up exactly where the last successful run left off, tracked through a set of small state files committed alongside the code (or, for the larger Hyperliquid buffer, cached rather than committed — see above). update.yml also runs a second way: immediately after every hyperliquid-update.yml completion (a workflow_run trigger, added 2026-09-11 — see "The two update workflows can race" below), on top of its own hourly cron.

Per-run manifests

Each run of run_incremental.py writes one small JSON file to data/manifests/, named by timestamp and GitHub Actions run ID (2026-09-15_070203_18234561234.json) — a self-contained record of what that specific run actually did, independent of reading the generated dashboard or digging through git log on the state files. It exists because diagnosing a real production issue (Base L2's growing backlog, traced in September 2026) required exactly that kind of archaeology — a manifest would have shown the block range and the count against the per-run cap directly.

Raw trade archive (Cloudflare R2 + Parquet)

trade_buffer.csv, base_trade_buffer.csv, and the Hyperliquid buffer are all rolling — trimmed to the classification lookback window on every run (see above). Nothing keeps the full history of raw transactions permanently: once a trade rolls off one of those buffers, it's gone, and the only way to get it back is to re-fetch it from RPC — slow, and not always possible if a node has pruned that far back.

live/lake.py closes that gap. On every run, right after each source's new trades are fetched (and before the buffer is trimmed), it archives exactly that run's delta as one Parquet file in a Cloudflare R2 bucket, partitioned by source and date: 

trades/
  source=uniswap_mainnet/date=2026-09-15/part-<run_id>.parquet
  source=base/date=2026-09-15/part-<run_id>.parquet
  source=hyperliquid/date=2026-09-15/part-<run_id>.parquet

This is entirely optional and additive — it requires three GitHub secrets (R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY) pointing at a Cloudflare R2 bucket with an API token scoped to it. Exactly like ALCHEMY_BASE_RPC_URL for Base, if any of the three secrets is missing, live/lake.py detects that and silently skips archiving — the rest of the pipeline, including the live dashboard, is unaffected either way. Any error during the upload itself (network, bad credentials, R2 outage) is caught inside upload_trades() and logged, never allowed to interrupt scoring — the mainnet path in particular has no surrounding try/except of its own (see Reliability lessons), so this function is written to never raise. (A gap in that guarantee — client construction itself ran before the try block, so a bad-credentials error at that exact point could still escape uncaught — was found and closed 2026-09-17.) The bucket name itself isn't secret — it defaults to hydra-terminal-lake, overridable with the (non-secret) HYDRA_R2_BUCKET environment variable.

Every successful upload is also recorded in that run's manifest (see above) under lake_objects — the exact key written and row count for each source — so a manifest doubles as a pointer into the archive: "what Parquet file backs this run's numbers" is a direct lookup, not a guess.

Resetting the win-rate counter

The "Signal history" card's compounded result / win-rate summary (see Reading the terminal) is computed entirely client-side in template.html::renderAggregateStats() from every closed LONG/SHORT streak ever recorded. data/stats_reset_state.json is an optional, hand-edited config file — nothing in the pipeline writes it — that lets a maintainer move the starting point for that one summary forward without touching anything else: 

{"reset_from_block": 25878499}

Streaks that started before that block are excluded only from the compounded result / win-rate numbers; the price chart, the full candle history, and the "Signal history" table itself are entirely unaffected — this is a narrow, reversible filter on one summary stat, not a data deletion. Useful after a real bug that corrupted past results — a sign error in how a SHORT streak's outcome was scored was exactly this kind of case earlier in the project's history — or simply to start a clean baseline from a chosen date. Delete the file, or omit reset_from_block, to go back to counting the full history.

Reliability lessons

A few hard-won rules now shape how new data sources get added to this project. They're worth knowing before extending the pipeline:

RPC throughput is shared, not partitioned

The Alchemy account used for both Ethereum and Base RPC calls has a single, account-wide throughput budget — it is not split per chain. Heavy usage on one chain can silently degrade or outright break calls on another. Any new RPC-heavy source has to be treated as competing for the same limited budget as everything that already works.

Order the risky thing last

A new, less-proven data source is always positioned in the code to run after the established, trusted path has already completed and saved its results — never before it. That way, even a catastrophic failure in the new part can only ever harm itself. This has a real, accepted cost when that source's output feeds back into the blend: Base's scoring step runs at the very end of main(), so by the time it computes a fresh composite_base, this run's own candles are already generated — the value only reaches the blend on the next run (see Data source: Base L2). A deliberate one-run lag was judged preferable to reordering the script and reintroducing this exact incident.

Partial failure is silent by design — and that's a trade-off

RPC calls that fail even after retries are logged as a warning and skipped rather than aborting the run (better a slightly incomplete window than no data at all) — but that means a fully "green" successful run can still be quietly discarding a meaningful fraction of real trades. When something on the dashboard looks off (an unusually low active-wallet count, for instance), the run's own log — specifically any UWAGA-prefixed warning lines — is the first place to check before assuming the market itself went quiet.

Verify against reality, not assumption

When a number on the dashboard looks wrong, the project's standing rule is to check it against an independent, real source — Etherscan/Basescan's own event logs, DexScreener's volume figures — rather than guessing whether it's a code bug or genuine market behavior.

The two update workflows can race (fixed 2026-09-11)

update.yml reads Hyperliquid's trade buffer from a GitHub Actions cache entry that hyperliquid-update.yml only writes once its ~50-minute WebSocket listen finishes. The two crons were offset (minute 7 vs. minute 20) purely so the jobs wouldn't compete for runners in the same minute — nobody had worked out that 20 + ~50 pushes the listener's finish to around minute 10 of the next hour, a few minutes after update.yml's own minute-7 run had already read the previous, hour-old cache entry. The result: every hourly refresh used Hyperliquid data that was structurally guaranteed to be almost an hour stale, not just occasionally unlucky. A fixed cron offset can't fully fix this — the listen duration isn't perfectly constant, and GitHub can delay a scheduled run's actual start under load. Instead, update.yml now also triggers via workflow_run immediately after every hyperliquid-update.yml completion (success or failure — the cache-read step already falls back to the latest available entry either way), on top of keeping its own hourly cron as a fallback. In practice the site now often refreshes twice within a few minutes of each other after an hourly cycle: once on schedule (possibly on stale data), then again right after Hyperliquid lands, self-correcting without waiting for the next hour.

...and that fix doubled how often two runs can genuinely collide (fixed 2026-09-17)

Running update.yml roughly twice per hour instead of once (previous entry) raised a different problem: two separate runs starting from the same committed state, each independently fetching new on-chain blocks and recomputing its own new candle/EMA state, before either has pushed. Git's own push-rejection retry (added back in the original "harden the workflow" pass) was designed for a person hand-editing a file on GitHub mid-run — git rebase onto whatever landed first, and abort loudly only on a genuine line-level conflict. Two automated runs racing each other isn't that kind of conflict: both commits are independently correct snapshots of the same rolling state files (candles_history.json, scoring_state*.json, trade_buffer.csv, site/index.html) computed from overlapping block ranges — there's no line-level merge of two such snapshots that means anything, so the rebase reliably hit a real content conflict and the job aborted. That's most of what pushed the visible failure rate up right after the workflow_run trigger above shipped.

The fix distinguishes why a push was rejected before deciding how to react: if the remote tip is another commit matching "Automatyczna aktualizacja danych...", this run's own local commit is simply stale — someone else already published fresher (or at least equally-fresh) data from the same chain state — so it's discarded outright (git reset --hard origin/main) and the job exits cleanly. Nothing is lost: any block this run processed that the other run didn't will simply be re-fetched and scored on the next run, the same way an aborted eth_blockNumber retry leaves nothing half-written (see "Partial failure is silent by design" above). Only when the remote tip is not an automated data commit — a real manual edit — does the workflow still attempt the rebase, and still abort loudly on a genuine conflict, exactly as before.

Reading the terminal

The dashboard is a single static HTML page with no client-side API calls — all the data it shows is baked in at build time by build_site.py.

Frontend redesign (2026-09): the layout below replaces an earlier version that surfaced every raw number (tracked/active wallet counts, a composite score, a BULL/BEAR tug-of-war score) as its own always-visible stat tile. Nothing was removed — every one of those numbers is still on the page — but most of it now lives in small print or behind a hover/tap (i) icon instead of competing for attention with the signal itself. Its main sections, top to bottom:

Since the "Long term (30d)" phase, a Main / Long term tab pair sits above the hero and switches every section below between the two classification tracks — see Long term (30d) classification track for how that works and what an empty tab means.

  • Composite meters — three plain-language gauges (blended, spot, Hyperliquid perp), each a one- or two-word read of direction and strength (e.g. "Wyraźnie niedźwiedzi") plus a centered bar, instead of a raw signed number. Tracked/active wallet counts are shown the same way, top-right of the card. Ja nie rozumiem."), and specifically asked to focus the line on capital's effect rather than the mechanics. The underlying numbers aren't gone, just demoted to the same (i) tooltip convention used everywhere else on the page — hover or tap it for the two raw composite values plus a one-line refresher on the square-root/cap mechanism. The word choice (same-direction "amplifies"/"softens" vs. opposite- direction disagreement) is decided in describeCapitalImpact() using the same signalThreshold already used to decide "Neutralnie"/"Wyraźnie"/"Silnie" on the composite meters above — one threshold, reused, not a second magic number. The line stays hidden — the same display:none graceful-degradation pattern as everywhere else on this card — for any candle predating this phase or produced by a run that never activated the volume-weighted track. Since 2026-09-13, each of the three source rows (Uniswap, Base, Hyperliquid) in the breakdown table also carries a small, muted timestamp of its own — the project owner noticed the three sources can legitimately describe different moments (Base's counts come from the previous pipeline run, a deliberate ~1-hour lag described in Data source: Base L2; Hyperliquid's depend on when its WebSocket listener last finished a window; only Uniswap's timestamp matches the candle's own) and asked for that to be visible rather than implied. Uniswap reuses the candle's existing time field; Base and Hyperliquid get two new candle fields, baseWindowTime and perpWindowTime, each the same DD.MM.YYYY, HH:MM (Warsaw time) format used everywhere else on the page, computed from that source's own window-closing block (Base: a new eth_getBlockByNumber call mirroring the existing mainnet one; Hyperliquid: its already-computed window_end_ts_ms, simply formatted). Deliberately plain, secondary-colored text — no highlight color — since the point was legibility of the underlying "as of when" fact, not drawing extra attention to it. Either field is null whenever that source has no data yet (unconfigured, immature, or a candle predating this phase), and the label is then omitted entirely rather than showing a confusing placeholder — the same graceful-degradation convention used throughout this card.
  • Dzienny bilans GOOD/BAD (daily GOOD/BAD balance) — added 2026-09-17, sitting between the Wallets card and the price chart. The project owner asked to see GOOD and BAD buy/sell activity summed per calendar day rather than per ~1-hour window, with a range switch (1D/7D/30D/90D/WSZYSTKO) plus an exact-date picker, and — after seeing a first mockup with placeholder numbers — one explicit condition before any of it shipped for real: the data has to be genuinely real, never invented. Two GOOD/BAD columns, each showing a day-bucketed bar chart (buy bars up, sell bars down from a shared zero line, independent vertical scale per column so BAD's usually-much-larger sell volume doesn't visually flatten GOOD's bars to nothing) plus Kupuje/Sprzedaje/Netto stat tiles above it, wallet-count total first and a smaller real-dollar figure underneath. The (i) tooltip is deliberately specific about what the wallet-count number actually is: a sum, across every ~1-hour classification window that calendar day (00:00–24:00 UTC) and across all three sources together, of how many GOOD/BAD wallets had a net-buying or net-selling direction that window — not a count of individual trades, and not a count of distinct wallets for the day (a wallet active in several windows the same day is counted once per window, deliberately, since that's what the underlying candle fields have always recorded). An earlier design mockup's own tooltip copy described this as "liczba transakcji" (a transaction count) — an acceptable simplification for a placeholder-data preview, but not something the real card could say once it was wired to real fields, so the copy was corrected before shipping. The USD figure underneath each count is a real dollar sum (see the addendum on good_buy_usd and friends in Composite score), but — because that field only starts accumulating the first run after this phase deployed — it reads as exactly $0 for every day before deployment, never an estimate. The card deliberately ignores the Main/Long term tab switch above it (see Long term (30d) classification track): every field it reads (goodBuyers, good_buy_usd, etc.) is inherently tied to the main 7-day classification track already, so the card is the same regardless of which tab is active elsewhere on the page.   • Price chart — signal-colored bands with a hover crosshair, plus a regime ribbon and event markers along the bottom. Unchanged from the previous layout.
  • Nastrój rynku (market mood) — a deliberately reduced, plain-language read of the regime detector: a one-line mood ("Rynek rośnie"/"Rynek spada"/"Bez wyraźnego kierunku"), a Spadki/Wzrosty pressure bar with no raw score attached, and the latest regime event, if any, again in plain language (with its technical name and confidence in small print underneath). The technical detail this used to show inline — BULL/BEAR score history (sparkline), momentum horizon, wallet-flip counts, and the calibration caveat — was dropped here rather than tucked away, at the project owner's explicit request once the plain-language version existed; it is not shown anywhere in the new layout. Two time indicators appear in the hero and are easy to conflate but measure different things: the candle's own price timestamp (which lags the wall clock by design — see Candles & windows), and the topbar's freshness indicator, which reflects when the pipeline itself last ran successfully.

Design system

A single, deliberately dark theme ("cinematic," per the project's own brief) — there is no light mode. Bebas Neue is used for the wordmark and section headers, IBM Plex Sans for body copy, and IBM Plex Mono for every number — prices, block heights, percentages, scores.

Regime colors were originally kept deliberately separate from signal colors (a violet for bear rather than reusing red) so a viewer would never confuse "the market's long-term regime" with "what to do right now" at a glance. That still holds for the price chart's regime ribbon and event markers (violet/amber, unchanged) — the chart already carries the green/red LONG/SHORT signal bands, so giving regime its own hue there avoids two different concepts sharing one color. Hover/tap-to-explain (.info-tip): the project's one and only tooltip convention — a small ⓘ icon (class="info-tip", a data-tip="..." attribute holding the explanation) that reveals its text on hover, or on tap on touch devices (a shared click handler toggles a .tip-open class, since :hover alone doesn't exist there). Running it locally

  1. Clone the repo: git clone https://github.com/bezplum-source/hydra-terminal.git
  2. Install Python dependencies (check requirements.txt in the repo root for the exact pinned versions — the core engine depends on pandas and numpy).
  3. Run the test suite: pytest tests/ -q. This is the fastest way to confirm your environment is set up correctly and that nothing is broken — every phase described in this document shipped with its own tests, and the suite is expected to stay green.
  4. To run the live pipeline locally, you'll need an RPC endpoint (an Alchemy app works well — see Environment variables) and to run python live/run_incremental.py directly.

You don't need any of this just to read or reason about the code — the engine in hydra_signals/ is pure logic with no network calls, and its test suite exercises it entirely offline with synthetic data.

How changes are made

A few conventions this project has settled into, useful to know before sending a change:

  • New data sources roll out in phases (collect → classify → blend → surface, see Current status) rather than landing fully wired-in on day one. Each phase ships independently, gets applied and confirmed working before the next one starts.
  • A new source is isolated first, integrated later. Its collection code lives behind a try/except boundary of its own, writes to its own state files, and is positioned to run after any already-trusted path in the same script — so it can never take down what already works (see Reliability lessons).
  • No look-ahead bias, ever, in anything that classifies a wallet or scores a window — see Classifying wallets.
  • Every change ships with tests, and the full suite (pytest tests/ -q) is expected to pass with zero regressions before anything is considered done.
  • Verify against the real, live repo state before assuming a previous change actually landed — this project has been burned before by reasoning about code that looked right locally but hadn't actually been applied on GitHub yet.

Glossary

Wallet / addressA public Ethereum (or Base) account identifier, not tied to a real-world identity.
SwapA trade against a DEX liquidity pool; emits a public on-chain Swap event.
GOOD / BAD traderThe top / bottom ~15% of tracked wallets, ranked by historical P&L and win rate.
Composite scoreThe blended measure of good-vs-bad wallet buy/sell pressure that drives the signal.
Candle / windowA fixed 250-block aggregation period on mainnet (~50 min), the base unit of the whole pipeline.
SignalThe short-term LONG / SHORT / HOLD call shown in the hero.
Market regimeThe longer-term BULL / BEAR / NEUTRAL read, independent of the short-term signal.
Wallet flipA wallet reversing its trading direction after a sustained streak the other way — a regime-model input.
Perp (perpetual)A leveraged derivative tracking an asset's price with no expiry; Hydra tracks Hyperliquid's ETH-PERP market.
Layer 2 (L2)A separate, faster/cheaper blockchain that settles back to Ethereum for security; Base is the L2 currently being added.
Incremental runA pipeline execution that resumes from saved state rather than reprocessing history from scratch.
Look-ahead biasUsing future information to make a past classification — strictly forbidden throughout this codebase.
