Hydra Terminal

Hydra Terminal watches what specific crypto wallets actually do on-chain — not what people say, not sentiment, not price alone — and turns that into a live LONG / SHORT trading signal and a BULL / BEAR market-regime read for ETH. This page explains the idea, the mechanism, and the codebase, for anyone joining the project without a crypto background.

Ethereum mainnet — live Hyperliquid ETH-PERP — live, blended into signal Base L2 — data collection only (B0)

Overview

At the highest level, Hydra runs an hourly pipeline that: pulls raw trade data from three independent sources, scores every wallet it has seen as a historically GOOD or BAD trader, aggregates what those two groups are doing right now, and turns that into two separate outputs — a short-term trading signal and a longer-term market regime — which are published to a static dashboard.

Nothing here predicts price from price. The entire bet the project is making is that a cohort of wallets with a strong historical track record behaves as a leading indicator: when they start buying before everyone else, the aggregate signal should tend to lead the market rather than follow it. Whether that bet actually holds is an open, ongoing empirical question — not an assumption baked into the code.

Where this comes from

Hydra Terminal is a from-scratch reconstruction of the mechanism behind hydra.trading, a site that published a live ETH signal derived from classifying DEX wallets into good/bad cohorts. The original project's source and infrastructure were lost, so this codebase re-derives the approach from first principles — reading the same on-chain events, applying the same kind of classification and scoring logic, and rebuilding the pipeline as open, auditable, public code rather than a black box.

The project has since grown beyond the original single-pool design: it now blends a second, independent data source (perpetual futures on Hyperliquid) into the same signal, and is in the process of adding a third (Base, an Ethereum Layer 2), specifically to grow the pool of wallets being tracked and to see whether the signal holds up across venues.

Both Hyperliquid and Base follow the same four-phase rollout pattern, so you'll see it referenced throughout this codebase and its history:

Phase 0 — Collect

Pull raw trades into an isolated buffer. No effect on the live signal yet.

Phase 1 — Classify

Score wallets from that source as GOOD / BAD, same method as mainnet.

Phase 2 — Blend

Merge that source's composite score into the signal the dashboard shows.

Phase 3 — Surface

Give the new source its own diagnostic card on the frontend.

Why phase it like this

Every new data source is wired in fully isolated at first — its own state file, its own error handling, its own code path — specifically so that a problem with a brand-new, unproven source (a bad RPC endpoint, a rate limit, a parsing bug) can never take down the mainnet pipeline that's already working. Only once a source is collecting cleanly does it get promoted to actually influencing what a viewer sees.

Core concepts: wallets & addresses

On Ethereum (and Base, which is built to be compatible with it), an account is identified by an address — a 42-character hex string like 0x4200...0006. There's no name, email, or KYC attached to it at the protocol level; anyone can generate one for free. A single person can control any number of addresses.

Every transaction sent from an address is public, permanent, and free for anyone to read — that's the entire premise the project rests on. Hydra doesn't need permission or an API key from any exchange to see what a wallet is doing; it reads the same public ledger everyone else can read, just at scale and automatically.

Hydra never tries to attach a real-world identity to an address. It only cares about one thing per wallet: given its trading history, was this address historically a good or a bad trader?

Core concepts: DEX pools & swaps

A DEX (decentralized exchange) like Uniswap doesn't match buyers with sellers order-book style. Instead, it uses a liquidity pool: a smart contract holding a reserve of two tokens (here, WETH — wrapped ETH — and USDC, a US-dollar stablecoin). Anyone can deposit both tokens into the pool to earn trading fees; anyone can trade against that reserve at any time.

A swap is a trade against that reserve: send USDC in, receive WETH out (a buy of ETH), or the reverse (a sell). Every swap emits a public Swap event on-chain, containing the pool, the amounts of each token, and the address that triggered it. That event is the single raw ingredient the mainnet and Base data collectors read — nothing more exotic than "who swapped how much, which direction, when."

Hydra specifically tracks the Uniswap V3 USDC/WETH 0.05% fee pool — one of the deepest, most actively traded ETH/USD venues on Ethereum, chosen and verified directly against the on-chain contract rather than assumed from a third-party list.

Core concepts: perpetuals

A perpetual future ("perp") is a derivative contract that tracks an asset's price without ever settling or expiring — traders open long or short positions with leverage, and a funding-rate mechanism keeps the contract's price tethered to the real spot price. Unlike a DEX swap, a perp trade doesn't require actually owning the underlying asset.

Hyperliquid is a decentralized perpetuals exchange, and one of the largest venues for on-chain perp trading. Hydra tracks its ETH-PERP market specifically — a completely different population of traders than the spot Uniswap pool, since perp traders and spot traders are often different people with different behavior. That's the whole reason it was added: to grow and diversify the wallet base beyond a single pool on a single chain.

Technically, Hyperliquid doesn't offer a REST endpoint for "everything that traded in the last hour" the way a block-based chain does — discovering new wallets requires a persistent WebSocket subscription to its public trade firehose, which is why the Hyperliquid side of the pipeline runs as a long-lived listener rather than the hourly "wake up, ask, go back to sleep" pattern used for mainnet and Base.

Core concepts: what is a Layer 2

Ethereum's own capacity is limited, which makes transactions there relatively slow and expensive. A Layer 2 (L2) is a separate blockchain that processes transactions independently but periodically settles back to Ethereum for security — cheaper and faster, while still inheriting Ethereum's guarantees.

Base is an L2 built by Coinbase. It has its own block numbers, its own block time (~2 seconds, versus Ethereum's ~12), and its own instance of the same Uniswap V3 contracts — including a WETH/USDC 0.05% pool, verified on-chain the same way as the mainnet one. Because it's a separate chain, its block numbers aren't comparable to Ethereum's at all, which is why Base is tracked as a fully independent data stream with its own cursor and buffer rather than mixed into the mainnet one.

Classifying wallets: GOOD / BAD

Every wallet Hydra has seen trade gets a rolling profit-and-loss (P&L) calculated with an average-cost method (covering both long and short exposure), plus a win rate across its trades. Wallets are then ranked against each other by that historical performance and split into three cohorts:

  • GOOD — roughly the top ~15% by historical performance.
  • BAD — roughly the bottom ~15%.
  • NEUTRAL — everyone in between; not used in scoring.

This classification is recalculated periodically as new data comes in (roughly every 250 blocks on mainnet, on the order of an hour), and — critically — a wallet is only ever classified using information available up to that point in time. Its future trades are never used to judge its past behavior. This "no look-ahead" rule is enforced deliberately, because without it a backtest of this whole approach would be meaningless — it would just be fitting to the answer.

Why this matters for the science, not just the code

The entire hypothesis under test is "does the aggregate behavior of historically-good wallets predict future price action." That's only a real test if the classification at time T could not have known what happens after T. Every classification pass in this codebase respects that boundary.

Composite score

For each scoring window, Hydra measures net buy/sell pressure separately for the GOOD cohort and the BAD cohort — essentially, "of all trading volume from good wallets this window, what fraction was buying versus selling," and the same for bad wallets. Those two pressures are smoothed with a short and a long exponential moving average (EMA) each, giving four tracked indicators per window, and combined into a single composite score: positive when good wallets are net buying (and/or bad wallets are net selling), negative in the opposite case.

Because two independent sources now feed the pipeline — the spot pool on mainnet and the ETH-PERP market on Hyperliquid — there are technically two composite scores, blended into one: 

composite_final = blend(composite_spot, composite_perp, weight=0.5)

with a graceful fallback to composite_spot alone whenever the perp side doesn't yet have enough data to be considered statistically mature — so a slow day on one source never silently corrupts the signal, it just quietly leans more on the other.

Candles & windows

Mainnet data is aggregated into fixed 250-block windows (roughly 50 minutes at Ethereum's ~12-second block time) — the same unit hydra.trading's original engine used, recognizable in this codebase as a "candle." A window only becomes a scored candle once enough blocks have passed beyond it to be confident it's complete; this is a deliberate, by-design lag, not a bug — it means the timestamp on the terminal's most recent candle will typically read 40–50 minutes behind the wall clock, even though the pipeline itself may have run only minutes ago. The separate "data last updated" indicator in the dashboard's topbar tracks the actual last successful pipeline run, distinct from the candle's own window-close time.

The signal: LONG / SHORT / HOLD

The blended composite score, once smoothed, is compared against a threshold to produce the headline signal shown in the terminal's hero: LONG, SHORT, or HOLD when neither side has enough conviction. The signal persists until the composite score moves decisively enough in the other direction — it isn't recomputed from scratch as a coin flip every window, which avoids flipping back and forth on small, noisy swings (the same hysteresis idea used for market regime, described next).

The dashboard also tracks every past signal period as a "streak" and reports its outcome — did the price move in the direction the signal implied by the time it ended — plus a running win rate across all closed streaks. That's the project's own scoreboard for whether the underlying hypothesis is actually working, kept visible rather than hidden.

Market regime: BULL / BEAR / NEUTRAL

The signal answers "what should I do right now" — it says nothing about the broader environment. A second, fully independent model answers a different question: "what kind of market are we in?" It's possible (and meaningful) for the regime to read BULL while the short-term signal is SHORT — a bullish backdrop with a short-term pullback — and the two are deliberately never conflated on the frontend.

Regime detection looks at the same GOOD/BAD cohort data but focuses on change over time rather than a single snapshot: is buy/sell pressure from good wallets improving or deteriorating across multiple horizons (1h out to 30d), is there a growing divergence between what good and bad wallets are doing, and how many individual good wallets have just flipped direction (e.g. closing a short streak and opening a buying one). Those signals feed two 0–100 scores, BULL_SCORE and BEAR_SCORE, which only produce a regime once they clear a threshold and hold for several consecutive windows — a persistence requirement that exists specifically to prevent a single noisy candle from flipping the whole regime read.

Two additional, rarer events are tracked on top of BULL/BEAR: CAPITULATION (bad wallets selling hard while good wallets are absorbing that supply — often a precursor to a bull transition, not the transition itself) and DISTRIBUTION (the mirror case — good wallets quietly selling into bad wallets buying, often ahead of a bear transition). Both are shown in a dedicated regime event log on the dashboard.

Data source: Ethereum mainnet

The original and still primary source: Swap events from the Uniswap V3 USDC/WETH 0.05% pool, read via JSON-RPC (eth_getLogs plus transaction lookups to resolve the real sender). Because the RPC provider used (Alchemy, free tier) hard-limits eth_getLogs to a 10-block range per call, the collector issues many small ranges as a single batched JSON-RPC request rather than hundreds of individual round trips, with automatic retry on any call that fails or gets rate-limited.

Data source: Hyperliquid (ETH-PERP)

A persistent WebSocket listener subscribes to Hyperliquid's public trades channel for the ETH market, which streams every trade with both counterparties' addresses. Collected trades are buffered (currently a 7-day retention window, to match the reputation window used on the mainnet side) and periodically classified with the same wallet-scoring method as mainnet, entirely independently — Hyperliquid has its own state files, its own classification pass, and its own composite score, which is only combined with the mainnet one at the very last step described above.

Because the buffer can grow larger than GitHub's 100MB-per-file push limit, it is deliberately kept out of git history entirely and stored instead in GitHub Actions' own cache between runs.

Data source: Base L2 Phase B0

The newest and currently least mature source. Base's Swap events from its own WETH/USDC 0.05% Uniswap V3 pool are collected the same way as mainnet (batched eth_getLogs), but into a completely separate buffer and block cursor — Base's block numbers have nothing to do with Ethereum's, and its ~2-second block time means covering the same wall-clock window costs roughly 6x as many RPC calls as mainnet does.

At this phase, Base data is collected only — it isn't classified, it doesn't touch the composite score, and nothing on the dashboard reflects it yet. That's intentional: the same staged rollout used for Hyperliquid (collect → classify → blend → surface) is being followed again here, and Base hasn't been promoted past step one yet.

A real incident worth knowing about

On Base's very first live run, its own RPC burst was large enough to exhaust the shared Alchemy account's throughput budget so badly that it broke the mainnet pipeline's own critical call, aborting the entire run with zero data saved — even for the parts that had nothing to do with Base. The fix was architectural: the Base collection step was moved to run strictly after the mainnet+Hyperliquid path has already finished and saved its results, so a Base-side problem can now only ever affect Base's own data, never anything that already succeeded. See Reliability lessons below — it's a pattern worth understanding before touching this part of the code.

Automation & state

The whole pipeline runs unattended via GitHub Actions, on an hourly schedule for the mainnet/Hyperliquid-blend/Base run (update.yml), plus a continuously-running listener workflow for Hyperliquid's WebSocket feed (hyperliquid-update.yml). Each run is incremental: it picks up exactly where the last successful run left off, tracked through a set of small state files committed alongside the code (or, for the larger Hyperliquid buffer, cached rather than committed — see above).

State fileTracks
data/scoring_state.jsonMainnet block cursor, EMA state, last signal
data/regime_state.jsonRegime state machine (BULL/BEAR/NEUTRAL, streaks)
data/wallet_flip_state.jsonPer-wallet streak/direction, for flip detection
data/hyperliquid_scoring_state.jsonHyperliquid classification + composite_perp EMA
data/base_collector_state.jsonBase L2 block cursor
data/candles_history.jsonFull scored candle history rendered on the dashboard

On every run, once mainnet and Hyperliquid data are pulled and scored, live/build_site.py renders the static site/index.html from live/template.html, which GitHub Pages then serves as the live dashboard.

Reliability lessons

A few hard-won rules now shape how new data sources get added to this project. They're worth knowing before extending the pipeline:

RPC throughput is shared, not partitioned

The Alchemy account used for both Ethereum and Base RPC calls has a single, account-wide throughput budget — it is not split per chain. Heavy usage on one chain can silently degrade or outright break calls on another. Any new RPC-heavy source has to be treated as competing for the same limited budget as everything that already works.

Order the risky thing last

A new, less-proven data source is always positioned in the code to run after the established, trusted path has already completed and saved its results — never before it. That way, even a catastrophic failure in the new part can only ever harm itself.

Partial failure is silent by design — and that's a trade-off

RPC calls that fail even after retries are logged as a warning and skipped rather than aborting the run (better a slightly incomplete window than no data at all) — but that means a fully "green" successful run can still be quietly discarding a meaningful fraction of real trades. When something on the dashboard looks off (an unusually low active-wallet count, for instance), the run's own log — specifically any UWAGA-prefixed warning lines — is the first place to check before assuming the market itself went quiet.

Verify against reality, not assumption

When a number on the dashboard looks wrong, the project's standing rule is to check it against an independent, real source — Etherscan/Basescan's own event logs, DexScreener's volume figures — rather than guessing whether it's a code bug or genuine market behavior.

Reading the terminal

The dashboard is a single static HTML page with no client-side API calls — all the data it shows is baked in at build time by build_site.py. Its main sections:

  • Hero — current signal (LONG/SHORT/HOLD), price, and how the active signal has performed since it started.
  • Stat grid — tracked/active wallets, the scoring pool size, and the composite score broken into spot / perp / final.
  • Regime card — BULL/BEAR/NEUTRAL, bull/bear score tug-of-war, confidence, and recent wallet flips.
  • Event log — START/END BULL/BEAR, CAPITULATION, DISTRIBUTION.
  • Price chart — signal-colored bands with a hover crosshair.
  • Signal history — every closed LONG/SHORT streak with its realized outcome, plus a compounded win-rate summary.

Two time indicators appear in the hero and are easy to conflate but measure different things: the candle's own price timestamp (which lags the wall clock by design — see Candles & windows), and the topbar's freshness indicator, which reflects when the pipeline itself last ran successfully.

Design system

A single, deliberately dark theme ("cinematic," per the project's own brief) — there is no light mode. Bebas Neue is used for the wordmark and section headers, IBM Plex Sans for body copy, and IBM Plex Mono for every number — prices, block heights, percentages, scores.

bg #0C0C10 bg-elevated #131318 accent #C4821E good/LONG #1FA65F bad/SHORT #B8253F regime bear #7C5CFF regime neutral #8A8894

Regime colors are deliberately kept separate from signal colors (a violet for bear rather than reusing red) specifically so a viewer never confuses "the market's long-term regime" with "what to do right now" at a glance — the two axes are independent by design, and the palette reinforces that.

Running it locally

  1. Clone the repo: git clone https://github.com/bezplum-source/hydra-terminal.git
  2. Install Python dependencies (check requirements.txt in the repo root for the exact pinned versions — the core engine depends on pandas and numpy).
  3. Run the test suite: pytest tests/ -q. This is the fastest way to confirm your environment is set up correctly and that nothing is broken — every phase described in this document shipped with its own tests, and the suite is expected to stay green.
  4. To run the live pipeline locally, you'll need an RPC endpoint (an Alchemy app works well — see Environment variables) and to run python live/run_incremental.py directly.

You don't need any of this just to read or reason about the code — the engine in hydra_signals/ is pure logic with no network calls, and its test suite exercises it entirely offline with synthetic data.

How changes are made

A few conventions this project has settled into, useful to know before sending a change:

  • New data sources roll out in phases (collect → classify → blend → surface, see Current status) rather than landing fully wired-in on day one. Each phase ships independently, gets applied and confirmed working before the next one starts.
  • A new source is isolated first, integrated later. Its collection code lives behind a try/except boundary of its own, writes to its own state files, and is positioned to run after any already-trusted path in the same script — so it can never take down what already works (see Reliability lessons).
  • No look-ahead bias, ever, in anything that classifies a wallet or scores a window — see Classifying wallets.
  • Every change ships with tests, and the full suite (pytest tests/ -q) is expected to pass with zero regressions before anything is considered done.
  • Verify against the real, live repo state before assuming a previous change actually landed — this project has been burned before by reasoning about code that looked right locally but hadn't actually been applied on GitHub yet.

Glossary

Wallet / addressA public Ethereum (or Base) account identifier, not tied to a real-world identity.
SwapA trade against a DEX liquidity pool; emits a public on-chain Swap event.
GOOD / BAD traderThe top / bottom ~15% of tracked wallets, ranked by historical P&L and win rate.
Composite scoreThe blended measure of good-vs-bad wallet buy/sell pressure that drives the signal.
Candle / windowA fixed 250-block aggregation period on mainnet (~50 min), the base unit of the whole pipeline.
SignalThe short-term LONG / SHORT / HOLD call shown in the hero.
Market regimeThe longer-term BULL / BEAR / NEUTRAL read, independent of the short-term signal.
Wallet flipA wallet reversing its trading direction after a sustained streak the other way — a regime-model input.
Perp (perpetual)A leveraged derivative tracking an asset's price with no expiry; Hydra tracks Hyperliquid's ETH-PERP market.
Layer 2 (L2)A separate, faster/cheaper blockchain that settles back to Ethereum for security; Base is the L2 currently being added.
Incremental runA pipeline execution that resumes from saved state rather than reprocessing history from scratch.
Look-ahead biasUsing future information to make a past classification — strictly forbidden throughout this codebase.
